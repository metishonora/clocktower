# #220 T13 spec 수정안 — action 의존 실행과 원본 UI

2026-09-12. **2026-09-12 사용자 승인 완료.** 사용자가 제안한 action의 의존 특성을 구체화한 설계안이다. [구현 계획](../plans/issue-220-t13-action-contracts-plan-draft.md)과 [29개 action 계약표](../plans/issue-220-action-contract-matrix.md)를 함께 검토한다. 이전 T13 초안의 특정 조합 묶음, 클릭 수에 따른 경계, 구현 중 결정받기 제안은 폐기한다. 별도 intent는 작성하지 않는다.

## 1. action이 선언하는 의존 실행

### D1. 단일 원본과 책임

각 action은 자기 선언에서 선행 action과 의존 출처를 명시한다. Core가 선언을 실제 occurrence/event에 연결하고, 진행 순서·표시·화면 연결·Undo가 같은 실행 정보를 사용한다. 캐릭터 이름, 같은 requiredInput, 인접한 사건, 네 조합 등의 별도 허용 목록으로 묶지 않는다.

- 캐릭터 규칙과 의존 선언은 Rust `characters/<script>.rs`에 둔다. 공통 registry/runtime은 선언을 검증·실행한다. 시스템 action은 system 등록이 소유한다.
- Core가 시나리오 순서, 참여/효력, 입력 합법성, 준비 필요 여부, 소유자/능력 인스턴스/모의 출처, 결과·효과·공개 허용 payload를 소유한다.
- Web은 action ID별 adapter로 원본 입력·결과·공개·복귀를 연결한다. 다음 action을 생성하거나 순서를 바꾸지 않는다.
- Session은 기존 propose/apply/replay/자동 저장과 stale 검증을 유지한다. 의존 실행은 여러 canonical 사건으로 기록할 수 있으며 사건을 하나로 합치지 않는다.

### D2. 의존의 의미와 선언

선행 데이터가 필요하다는 사실과 현재 실행을 이어 완성한다는 사실을 구별한다. action 선언에는 다음을 둔다.

1. **필수 선행 action:** 해당 action을 지금 실행하는 데 새 준비가 필요하면 기존 캐릭터 규칙이 구체적인 준비 occurrence를 제공한다. 소비 action이 선행 action ID를 선언하며, scheduler는 그 선언을 통해 준비를 소비 action의 시나리오 위치에 배치한다.
2. **후속 action의 출처:** 전달의 preparationEventId, 통지의 relationshipEventId, 능력 획득/모의 선택의 실제 source event처럼 기존 Core가 검증하는 출처로 선행 사건을 연결한다. 생성된 능력의 경우 실제 생성 사건의 action ID와 기존 활성화 결정을 함께 확인한다.
3. **현재 실행 연결:** 위 출처가 현재 열린 실행 안에 있고 Core가 지금 필요한 후속 action으로 배정했을 때만 같은 실행이다. 과거 완료된 준비값 참조, 미래 시나리오 위치에 배정된 획득 능력은 별도 실행이다.

각 action에 이 선언의 유무를 명시하며, 전체 매핑은 계약표 D 열이 기준이다. 동적으로 생성된 능력의 선행 action은 action 이름을 추정하지 않고 Core의 능력 인스턴스·simulationSource·followUpCause가 가리키는 사건에서 얻는다. 같은 소유자/인스턴스가 원칙이지만 능력 생성은 생성 사건이 증명한 이전→새 인스턴스 관계를 사용한다. 초기 setup 사건은 되돌릴 실행의 부모로 포함하지 않는다.

현재 catalog의 `linked_action`은 배치 위치에 대한 정보다. 이 표를 Undo 허용 목록으로 복사하지 않는다. 준비→소비 매핑은 위 선언에서 조회하고, `drunk.assignShownCharacter`의 철학자 위치 연결은 실행 출처로 대체한다. 모든 script별 판단은 기존 script 규칙 안에 유지한다.

### D3. 실행·화면·종료 경계

실행은 독립 root action과 그 action에 의존하는 실제 후속 occurrence들이다. 새 필수 준비가 있으면 준비부터 시작해 소비 action까지 같은 실행으로 이어진다. 같은 실행의 내부 action은 각각 검증·확정하지만 화면에 별도 준비 단계나 불필요한 진행 탭 왕복을 만들지 않는다. 진행 행은 Core가 제공한 사용자 행동 단위로 표시하며 내부 action 목록은 진단/테스트용으로 보존한다.

- 세탁부·사서·수사관: 자기 소유자의 준비와 전달을 마친 뒤 다음 소유자/직업으로 이동한다.
- 쌍둥이: 지정 뒤 마도서의 기존 공개 안내로 이어지고, 사용자가 공개를 열고 닫는다. 중간에 진행 탭과 추가 다음 버튼을 끼우지 않는다.
- 점쟁이: 현재 판정을 위해 새 붉은 청어 지정이 필요하면 지정 뒤 판정 대상 선택으로 이어진다. 지정 대상과 판정 대상 입력은 별개이며 초기 지정용 진행 복귀/재진입을 추가하지 않는다. 이미 유효한 붉은 청어가 있으면 판정만 실행한다.
- 생성된 능력: action에 선언된 생성 출처와 기존 Core의 즉시 실행 결정이 모두 있을 때 같은 실행을 잇는다. `JoinPendingOrder`는 본래 시나리오 위치에서 새 실행, `Defer/NoAction`은 현재 실행 대상이 아니다. 획득했다는 이유만으로 모든 후속 능력을 당겨 실행하지 않는다.

공통 controller는 Core의 **현재 action**만 소비한다. 필요한 선택/등록/정보 입력, 사용·보류, 공개 버튼과 확인/닫기는 해당 원본 계약대로 남긴다. 자동으로 비밀 공개를 열거나 사용자 입력을 대신 선택하지 않는다. 입력 없는 내부 연결은 중복 없이 처리할 수 있지만 공개 조작 자체는 생략하지 않는다.

후속 action이 없거나, 시나리오상 독립 action/다른 소유자 실행/자유 행동/phase 전환이 끼거나, 기존 규칙상 능력이 소멸·종료되면 열린 실행을 끝낸다. 연결된 과거 데이터를 나중에 읽더라도 그 실행을 다시 열어 중간 사건과 합치지 않는다. 입력 취소만으로는 이미 확정한 앞부분이 삭제되지 않는다. 재선택은 같은 현재 action의 미확정 입력을 바꾸며 확정 부분의 취소는 Undo로 한다.

### D4. Undo·오류·저장 복원

같은 실행에 속한 확정 사건은 Undo 한 단위다. 도중까지 확정한 실행도 확정 부분 전체를 한 번에 되돌린다. 아직 확정하지 않은 action이나 단순 공개 열기/닫기에 가짜 canonical 사건을 만들지 않는다. 한 번에 처리한다는 뜻은 사용자 행동/Undo 경계이며 모든 입력을 건너뛰거나 저장을 마지막까지 지연한다는 뜻이 아니다.

Core는 replay 중 각 실행의 root·parent·확정 사건 목록과 마지막 Undo 대상을 산출한다. Undo 대상은 현재 canonical 이력의 연속된 마지막 구간이어야 한다. 같은 이름/근접성은 의존 근거가 아니며 연속성 검사는 다른 사건을 침범하지 않는 보호 조건이다. 대상 ID는 마지막 확정 사건에 따라 바뀌어 부분 실행의 옛 확인창으로 더 큰 단위를 삭제하지 못한다. 초기 setupConfirmed는 제외한다.

Session은 Core가 준 대상과 최신 파일/stream의 일치를 검증한 뒤 해당 구간만 제거하고 replay·저장한다. 요약은 그 실행의 실제 행동자/행동을 사용자 문구로 표시한다. UI adapter나 TS canonicalUndo가 의존을 재추론하지 않는다.

- 후속 propose/apply 실패: 성공한 앞부분을 유지하고 같은 현재 action에서 재시도하거나 그 실행을 Undo한다. 성공한 앞부분을 다시 확정하지 않는다.
- 저장 실패: 기존 미저장 상태와 재시도 경로를 유지한다. 저장 완료로 표시하거나 다음 자동 확정을 계속하지 않는다.
- 새로고침/JSON/자동 저장 복원: 같은 사건 prefix에서 같은 실행/Undo 대상이 재구성된다. 미확정 입력·열린 비밀 공개는 재생성하지 않고, 현재 action 및 확인 가능한 확정 결과에서 재개한다. 확정된 공개는 기존 허용 payload로 재열람한다.
- 과거 저장의 초기 준비 prefix 및 ‘여러 소유자 준비→각 전달’ 기록은 그대로 replay한다. 끼어 있는 독립 사건을 넘어 묶지 않으며 해당 참조는 과거 데이터 참조다. 이력을 재정렬/재작성하거나 옛 파일에 새 실행 ID를 주입하지 않는다.

GameFile/사건/schemaVersion/저장 슬롯은 유지한다. 실행 metadata는 read-only replay projection으로 확장하며 JSON에는 저장하지 않는다. 기존 `informationFlow`는 호환 출력이 필요하면 같은 실행 모델에서 파생하고 새 UI의 판단 기준으로 병행 유지하지 않는다. 구버전 WASM 응답에 실행 계약이 없으면 기존 연결 오류로 처리하며 조용히 사건별 Undo로 돌아가지 않는다.

### D5. action별 UI 계약과 범위

[전체 29개 계약표](../plans/issue-220-action-contract-matrix.md)의 각 행을 별도 구현·검증 단위로 삼는다. 공통 shell·controlled view는 재사용하고 UI/규칙 엔진을 29벌 복제하지 않는다. 내부 action ID별 adapter는 입력 위치·완료/취소·공개 payload·수신자·닫기 목적지를 명시한다. 입력 kind가 같다는 이유로 범용 완료 동선을 쓰지 않는다.

원본 TB/SnV 직업별 동선과 BMR 테마를 사용하고 최신 사용자 정정을 우선한다. 새 UI가 필요한 것으로 드러나면 임의 구현하지 않는다. 이번 계획에는 미정 UI가 없으며, 새로운 요구가 발견된 경우는 승인 범위 변경으로 별도 spec 개정 대상이다.

T10–T12의 보정 강조, 상세 중복 태그 제거, 배치 복귀 제거, 선택 강조/두 명 조합 검증, 판정값 표기, 불필요한 정답 선택 제거, 공개 크기·첩자 원본 마도서 등은 유지한다. 변종 처형 확인 문구는 사용자 승인대로 기존 첫 문장만 사용한다.

## 2. 새 시나리오

사용자 확인: 새 게임 옆에 ‘새 시나리오’를 추가한다. 확인 후 선택 내용이 없는 시나리오 작성 첫 화면으로 돌아간다. 기존 자동 저장은 이 이동만으로 삭제하거나 빈 내용으로 덮어쓰지 않는다. 새 게임 저장은 기존 저장 슬롯/교체 정책을 따른다.

직업 설정·배치·진행·저장 화면의 동일 유틸리티 위치에 노출한다. 현재 시나리오를 유지하고 새 배역을 만드는 ‘새 게임’은 기존 동작을 유지한다. 공개 중에는 기존 유틸리티 잠금 기준을 따른다.

확인 UI는 BMR 새 게임 확인창 형태를 재사용한다. 문구 제안: 제목 ‘새 시나리오를 작성할까요?’, 본문 ‘현재 화면을 닫고 빈 시나리오 작성 화면으로 돌아갑니다. 기존 자동 저장은 유지됩니다.’, 버튼 ‘취소’/‘새 시나리오 작성’. 확인창의 문구까지 본 문안 승인 범위다.

확정 시 작성기의 이전 파일·초안·검토/오류·비동기 작업을 초기화하고 새 진입 상태를 만든다. 이전 게임 복원 navigation 표식을 제거해 새로고침으로 옛 게임에 강제 재진입하지 않는다. 저장 내용과 navigation 표식은 별개다. 기존 게임의 지연 응답이 새 작성 화면을 덮지 못하게 한다.

저장 중에는 완료 전 이동을 실행하지 않는다. 저장 실패로 아직 기록되지 않은 확정 사건이 있으면 기존 재시도 경로를 유지하고 오류를 보여주며 이동을 완료하지 않는다. 임의로 저장 성공 처리하거나 별도 삭제 선택지를 만들지 않는다.

| ID | 상황·조작 | 기대 결과 |
| --- | --- | --- |
| N01 | 각 마도서 탭에서 유틸리티 확인 | 새 게임 바로 옆에 새 시나리오. 좁은 화면에서도 원본 흐름으로 접근 가능 |
| N02 | 새 시나리오→취소/Escape | 탭·선택·진행·저장·작성기 모두 무변경, 포커스 복귀 |
| N03 | 확인 확정 | 빈 작성 첫 화면, 이전 이름/직업/순서/파일/검토 상태가 남지 않음 |
| N04 | 이동 후 새로고침 | 옛 게임으로 강제 복원되지 않음. 저장본 자체는 여전히 기존 경로로 불러올 수 있음 |
| N05 | 이동 후 새 게임 확정 전/후 | 기존 저장은 이동만으로 변하지 않음. 새 게임 저장 시 기존 슬롯 정책 적용, 추가 덮어쓰기 질문 없음 |
| N06 | 저장/가져오기/검증 지연, 실패, 반복 클릭 | 늦은 응답이 화면을 되돌리지 않음. 미저장 사건을 잃지 않으며 실패는 기존 복구 경로로 표시 |
| N07 | 기존 새 게임 실행 | 같은 시나리오 유지. 새 시나리오 동작과 혼동되거나 작성기로 이동하지 않음 |

## 3. Undo UI의 BMR 원본 복원

BMR production은 snvGlobalUndo와 empty 상태, 행동 요약을 포함한 접근성 라벨, 브라우저 기본 window.confirm을 사용한다. Custom 아이콘 SVG path 자체는 동일하며 새 도형 제작 대상이 아니다. Custom의 자체 GameConfirmationDialog를 원본 Undo 확인 방식으로 교체한다. 새 게임/새 시나리오의 BMR 형태 확인창과 Undo의 브라우저 기본 확인창은 원본처럼 구별한다.

- 행동 있음: ‘최근 행동 되돌리기: {사용자용 행동 요약}’. 없음: empty/비활성 및 ‘되돌릴 행동 없음’.
- 확인 문구: ‘최근 행동을 되돌릴까요?\n{사용자용 행동 요약}’. 내부 action ID/JSON/변수 이름은 사용자 문구로 노출하지 않는다.
- 요약은 실제 현재 Undo 대상과 같아야 한다. 취소는 무변경, 확정 후 기존 stale 검증·Core replay·자동 저장을 유지한다.
- UI 복원은 표시/확인 방식의 변경이다. 실제 Undo 대상과 요약은 1절의 Core 의존 실행 단위를 그대로 사용한다.

| ID | 상황·조작 | 기대 결과 |
| --- | --- | --- |
| U01 | 최초 확정 직후 되돌릴 행동 없음 | BMR empty 아이콘 상태·비활성·접근성 라벨 |
| U02 | 행동 완료 후 Undo | BMR 원본 위치/크기·요약 라벨, 동일 종류의 브라우저 기본 확인창 |
| U03 | 확인 취소/확정 | 취소는 사건 무변경. 확정은 표시한 현재 단위만 제거·replay·저장 |
| U04 | 확인 전후 대상 변경, 공개/명령 처리 중 | 기존 stale/busy/public 보호 유지, 다른 최신 행동을 잘못 취소하지 않음 |
| U05 | 과거 JSON 복원, 내부 ID가 있는 기록 | 사용자 요약으로 표시하고 실제 Undo 대상과 일치 |
