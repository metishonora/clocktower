## Spec v4 — #220 ([205-2]) 기존 SnV 마도서 기반 커스텀 시나리오·첫날 밤 연결

> 최신 승인·구현·인수 상태는 [최종 상태](../testing/issue-220-final-validation.md)를 따른다. 아래 과거 단계의 native confirm/배치 복귀 전체 제거/인수 대기 표현은 최신 기준으로 대체되었다.


7.4절은 이번 사용자 지시를 반영한 로컬 최신 보완이며 아직 이슈에 게시하지 않았다. 게시된 이전 기준: [갱신 Spec](https://github.com/metishonora/clocktower/issues/220#issuecomment-5628640924), [갱신 Plan·63개 조건](https://github.com/metishonora/clocktower/issues/220#issuecomment-5628643606). 이전 [v2 승인 기록](https://github.com/metishonora/clocktower/issues/220#issuecomment-5627693800)은 변경 이력으로 보존한다.

> 2026-09-11 추가 승인: 커스텀 마도서 전체의 시각 테마는 BMR로 통일한다. 아래 과거 SnV 테마 참조보다 이 지시가 우선한다. 시나리오 작성기 동선과 Core/저장 계약은 유지한다.
> 2026-09-11 구조 보완 승인: 기존 사용자 UI/동작을 유지하며 내부 연결 구조를 재설계할 수 있다. 시나리오 명시 순서 이행, 책임 경계, 추가 사례 A01–A06은 7.1–7.3절을 따른다. 사용자가 spec·plan 수정 및 이슈 기록을 요청했다.
> 2026-09-11 UI 재사용 재점검: BMR 전체 비교, 직업별 기존 UI 복원, 준비/전달의 단일 사용자 단계, 새 UI 사전 승인 요구는 7.4절이 우선한다. R3는 기존 판단 기록·복원까지 포함하고 합의된 아키텍처를 유지하는 것으로 확정했다.
> 상태: 기존 요구와 이번 명시적 사용자 지시 반영. 후속 구현 계획은 별도 승인 대상. 자동 저장은 별도 교체 확인 없이 새 게임/선택한 게임으로 대체한다는 후속 결정을 반영했다. 이 문서는 이전 Spec v2의 교체 확인 정책을 대체하며, 구현 완료를 뜻하지 않는다.

### 1. 기준과 문서 상태

2026-09-10 사용자 결정에 따라 [#205 원본 Spec](https://github.com/metishonora/clocktower/issues/205#issuecomment-5595997690)을 #220으로 복사·계승한다. #205 원본과 승인된 프로토타입은 변경하지 않는다. 이 문서는 아래 최종 승인 사항을 반영한 #220의 구현 기준이며, 원본의 내부 시나리오 보관 요구와 미결정 항목을 그대로 재도입하지 않는다.

- 작성·파일 계약: [#197 Spec](https://github.com/metishonora/clocktower/issues/197#issuecomment-5594316985)과 [완료 기록](https://github.com/metishonora/clocktower/issues/197#issuecomment-5595515155)
- 시각·상호작용: [#202 최종 승인 결과의 #205 반영](https://github.com/metishonora/clocktower/issues/205#issuecomment-5559777329), 그리고 2026-09-09 #205 시나리오 편집 최종 승인
- 최종 승인 근거: 보존된 `web/src/prototypes/issue205/NOTES.md`의 Current user decisions, compact source panel, direct JSON import, User approval 항목. #220에는 `docs/prototypes/issue-220/issue-205-editor-decisions.md`로 원문을 보존한다.
- 순서·저장 기반: [#198 Intent](https://github.com/metishonora/clocktower/issues/198#issuecomment-5559905991)
- 첫날 밤 실행: #203 및 #206–#209의 최종 승인 계약과 완료 결과
- 분기 경위: [#205 보류 기록](https://github.com/metishonora/clocktower/issues/205#issuecomment-5601329450), [#220 독립 연결 결정](https://github.com/metishonora/clocktower/issues/205#issuecomment-5619624031)

#202·#197·#203은 완료된 선행 기반이다. #205 초기 본문의 외부 공식 custom-script JSON 변환과 별도 Setup 행동 목록 요구는 적용하지 않는다. #197 기반의 실제 파일·검증 기능을 재사용하고, 편집 화면과 상호작용은 그 뒤 승인된 #205 최종본으로 맞춘다.

#220은 승인된 편집 흐름 뒤에 기존 SnV 형태의 마도서를 연결한다. #218의 이야기형 UI 승인에 의존하지 않는다. #218은 같은 커스텀 도메인·세션 연결을 사용하는 별도 표현으로 발전하며, 이 분기로 게임 규칙·저장 계약을 복제하지 않는다.

#205 편집 화면 승인과, 사용자가 검토 후 Spec 단계로 진행하기로 한 #220 대표 연결 프로토타입을 UI 근거로 사용한다. 재확인 가능한 화면은 `/clocktower/issue-220-prototype.html`, 검토 기록은 `web/src/prototypes/issue220/NOTES.md`와 `docs/prototypes/issue-220/connection/`에 있다.

확인된 연결은 최종 검토 → 로딩 → 기존 SnV 형태의 직업·마도서·진행 탭, 빈 actual roster에서 역할·좌석 설정, 첫날 밤 정보 공개·가리기·다음, exact-match 이어 쓰기다. 공개 중 이야기꾼 UI와 검토 도구를 숨기고, 가린 뒤 진행한다. 숫자 정보의 크기를 포함한 기존 SnV 표현을 유지한다.

프로토타입의 고정 분포표·5인 배역·숫자값·순서 필터·재개 위치·메모리 상태는 설계나 규칙 계약으로 채택하지 않는다. 모든 TB/SnV 첫날 밤 행동이 프로토타입에서 검토·실행됐다고 취급하지 않는다. 현재 부분 Setup 연결과 대표 예시는 실제 파일 처리·첫날 밤 전체 실행·지속 저장의 구현 완료를 뜻하지 않는다.

### 2. 사용자 흐름과 UI

1. Production Custom Scenario 진입에는 `새롭게 작성한다`와 `JSON에서 불러온다`만 제공한다. `저장본을 연다`와 앱 내부 시나리오 목록은 제공하지 않는다.
2. 새 작성은 시나리오 선택 → 캐릭터 설정·이름 → 밤 행동 순서 → 최종 검토로 이어진다. 이번 범위에서 편집·저장·실행하는 밤은 첫날 밤뿐이다.
3. JSON은 목적 선택 없이 하나의 진입점으로 불러온다. 성공하면 곧바로 최종 검토로 이동한다. 파일명·진행 요약·중간 검토 버튼·공식 마도서 분기 대화상자를 추가하지 않는다. 실패하면 파일 선택 화면에서 오류를 표시하고, 취소하면 현재 내용을 유지한다.
4. 최종 검토의 `시나리오 저장`은 즉시 JSON 다운로드를 요청한다. `새 마도서 쓰기`는 추가 확인 대화상자 없이 기존 TB/SnV 계열 로딩 전환을 거쳐 마도서 게임 설정으로 이동한다. 별도 Setup 행동 목록·첫날 밤 미리보기·추가 시나리오 확인 화면은 두지 않는다.
5. 참가자·좌석·Actual/Shown Character와 게임별 Setup은 기존 SnV 형태의 마도서에서 설정한다. 시나리오 후보 풀을 실제 참가 배역으로 자동 간주하지 않는다.
6. 복원 가능한 불러온 게임과 현재 편집본이 정확히 일치할 때만 `마도서 이어 쓰기`를 제공한다. 시나리오 파일만 불러온 경우에는 게임 진행 정보를 만들거나 재개를 활성화하지 않는다.

시작 패널은 내용에 맞는 높이로 화면 아래에 배치한다. 불필요한 별 장식·업로드 아이콘·도움말과 `스크립트 선택으로` 버튼을 재도입하지 않는다. JSON 파일 선택은 최소 44px 높이의 간결한 버튼을 유지한다.

#197에서 연결한 검색·필터·선택·상세, 위/아래 순서 이동, 고정 dusk/dawn, 기본값 복원, 반응형·키보드·터치·reduced-motion 동작을 유지한다. 드래그 재배치와 지속적인 단계 표시기는 추가하지 않는다.

최종 검토는 #205 최종 승인 기준의 이름 편집, 진영별 구성 수와 전체 캐릭터 아이콘·이름, 승인된 주요 행동을 유지한다. 밤 순서 요약·구성 수정 버튼·출처·상단 배지·일반 알림 패널을 다시 추가하지 않는다. 모바일에서는 내용과 행동·이전 단계 복귀에 하나의 흐름으로 접근할 수 있어야 한다.

이름 → 캐릭터 설정 → 밤 행동 순서 순으로 첫 차단 오류 하나를 표시한다. 15인 권장 후보 수 13/4/4/4 부족은 비차단 경고이며, 실제 게임 시작 가능 여부는 별도의 Setup 유효성에 따른다. 저장·불러오기·실행 실패에는 원인에 맞는 간결한 복구 동선을 제공한다.

### 3. 시나리오 파일

| 작업 | 보장할 결과 |
| --- | --- |
| 시나리오 저장 | #197과 동일한 앱 전용 JSON을 즉시 다운로드. 내부 시나리오 저장본이나 게임을 생성·교체하지 않음 |
| 시나리오 JSON 불러오기 | 파일의 이름·캐릭터 배열·첫날 밤 순서를 검증 후 복원하고 최종 검토로 이동. 진행 기록이나 이어 쓰기 자격을 만들지 않음 |
| 게임 진행을 포함한 지원 JSON 불러오기 | 별도 목적 선택 없이 검증 후 최종 검토로 이동. 유효한 커스텀 게임과 exact identity 일치 시에만 이어 쓰기 제공 |

시나리오는 자동 저장하거나 앱 내부에 별도로 보관하지 않는다. 저장본 목록·복사·교체·복구와 새 마도서 생성 중 시나리오 보관 선택을 추가하지 않는다. 게임 진행의 자동 저장은 별도 책임이며 6절 계약을 유지한다.

시나리오 파일에는 내부 저장 식별자나 게임 진행 기록을 추가하지 않는다. 같은 시나리오 파일을 반복해서 불러와도 기존 게임을 찾아 연결하거나 교체하지 않는다.

모든 다운로드와 새 마도서 생성은 현재 내용의 유효성을 기준으로 한다. 검증 이후 내용이 바뀌면 이전 성공 결과로 변경된 내용을 저장하거나 새 마도서를 만들 수 없다. 파일 선택 취소·읽기 실패·검증 실패와 늦은 비동기 결과로 현재 편집 대상을 덮어쓰지 않는 #197 계약을 유지한다.

### 4. 새 마도서와 게임 설정

- 새 마도서는 최종 검토에서 선택한 유효한 시나리오의 일관된 definition snapshot을 사용한다. 이후 별도 편집본의 변경을 진행 중 게임에 적용하지 않는다.
- 마도서의 게임 설정에서 참가자·좌석·실제 배역·Shown Character·bluff 후보와 인원별 진영 분포 및 Setup 변경 효과를 기존 커스텀 도메인 계약으로 검증한다.
- 실제 배역, 표시 배역, bluff 등 각 후보의 허용 조건은 기존 규칙을 따른다. 시나리오 밖 캐릭터를 선택하거나 사용하게 허용하지 않는다.
- 시나리오 후보 수 부족 경고와 실제 배역 구성 오류를 구분한다. 시나리오가 유효해도 실제 Setup이 유효하지 않으면 게임 시작을 거부하고 설정을 수정할 수 있게 한다.
- Setup 확정에 성공하면 해당 시나리오와 실제 게임 설정으로 첫날 밤을 진행한다. 거부된 설정을 일부만 적용하거나 성공한 것처럼 다음 단계로 이동하지 않는다.
- 게임별 행동 순서 편집이나 별도 순서 저장을 추가하지 않는다.

최종 승인대로 기존 게임이 불러와져 있어도 `새 마도서 쓰기`에서 추가 확인 없이 게임 설정으로 이동한다. 설정 화면에 들어가는 것만으로 기존 게임을 삭제하거나 덮어쓰지 않는다. 새 게임의 자동 저장은 12절 S1에 따라 확인 없이 기존 슬롯을 대체하며, 설정·저장 실패를 성공으로 처리하지 않는다.

### 5. 이어 쓰기와 게임 파일

**커스텀 게임**

- 이어 쓰기는 유효하게 읽고 전체 진행 기록을 복원할 수 있는 커스텀 게임을 대상으로 한다. definition 일치만으로 손상되거나 재생할 수 없는 게임을 재개하지 않는다.
- 게임 파일에 담긴 원래 definition과 현재 편집 대상이 기존 exact identity 계약에서 정확히 일치해야 한다.
- 기존 계약의 비교 대상은 `id`, `name`, 순서를 포함한 `characterIds`, 각 행동의 식별과 순서를 포함한 `firstNightOrder`다. 표시 문자열 정규화나 집합 비교로 동등성을 넓히지 않는다. 따라서 이름만 바꾸거나 캐릭터 배열 순서만 바꿔도 일치하지 않는다.
- 실제 참가하지 않은 후보 캐릭터를 변경해도 이어 쓰기를 허용하지 않는다. 현재 사용된 배역·과거 이벤트의 참조 여부만으로 비교 범위를 좁히지 않는다.
- 변경된 편집본에서는 새 마도서만 허용하고, 원래 값으로 정확히 되돌리면 이어 쓰기 가능 상태를 복구한다. 편집과 비교 과정에서 원래 게임을 변경하지 않는다.
- 시나리오 JSON에는 게임 identity와 진행 기록이 없으므로, 내용이 비슷하다는 이유로 기존 게임을 찾아 이어 붙이지 않는다.

**공식 게임과 파일 경계**

JSON의 사용자 진입은 하나로 통합하되 시나리오·커스텀 GameFile·공식 파일의 타입 및 검증 책임은 섞지 않는다. #197 시나리오 전용 판독기의 수용 범위를 무조건 넓히지 않고, 지원하는 커스텀 GameFile은 해당 검증·복원 경계로 처리한다.

공식 TB·SnV 게임의 재개는 기존 공식 화면·파일 계약에 남긴다. #220 편집기에 공식 게임 재개/커스텀 변환 선택이나 별도 공식 분기 화면을 만들지 않는다. 공식 게임을 커스텀 실행으로 변환하거나 커스텀 로딩 실패 시 공식 실행으로 우회하지 않는다. 지원하지 않는 파일은 간결한 오류로 처리한다.

게임 파일 검증·복원 실패는 기존 정상 게임과 현재 편집 내용을 보존하고 재시도할 수 있게 한다.

### 6. 첫날 밤·저장·복원

- 첫날 밤은 #203 및 #206–#209에서 승인된 행동·정보 전달·후속 결과를 기존 실행 경계로 제공한다. 새 캐릭터 규칙이나 별도 웹 판정을 추가하지 않는다.
- 시나리오의 명시적 순서와 행동 시점의 상태에 따라 실제 적용되는 행동을 처리한다. 시나리오에만 있는 행동을 실행하거나 필요한 다중 소유자·획득 능력 행동을 누락하지 않는다.
- 실행·복원 중 누락된 순서를 작성용 기본안으로 보충하지 않는다.
- 첫날 밤은 승인된 규칙에 따라 Day 또는 게임 종료 상태에 도달한다. 이후 밤 실행 및 낮의 일반 진행·능력 실행을 이번 UI 연결 범위로 확대하지 않는다.
- 자동 저장·새로고침·Undo·게임 파일 내보내기와 불러오기 후 동일한 definition snapshot과 확정 기록으로 동일한 상태·진행 위치·확정 당시 전달 정보를 복원한다. Undo 단위와 규칙은 기존 세션 계약을 따른다.
- 저장 실패는 게임 명령 거부나 파일 손상과 구분하며, 디스크에 저장되지 않은 상태를 저장 완료로 표시하지 않는다. 메모리에서 성공한 진행과 마지막 저장 상태가 다를 수 있는 경우 그 상태를 오인하지 않게 하고 재시도할 수 있어야 한다.
- 손상된 저장본이나 replay 실패를 정상 빈 게임으로 대체하지 않는다. 읽기·복원 실패는 오류로 표시한다. 사용자가 새 게임을 시작하거나 유효한 게임 파일로 이어 쓰면 12절 S1에 따라 자동 저장을 확인 없이 대체한다.

`definition.firstNightOrder`가 유일한 확정 순서이며 `createGame`·`setupConfirmed`에 별도 `firstNightOrderPlan`을 복제하지 않는다. Setup 행동 목록을 별도 UI나 저장 상태로 만들지 않는다.

커스텀 연결 계층은 편집 결과·Setup 입력·현재 세션·화면 상태 사이의 전환과 비동기 최신성을 조정한다. 이 계층이 외부 공용 표현 컴포넌트에 데이터와 콜백을 공급하고, 커스텀 도메인·세션 내부는 공용 UI나 공식 실행 코드에 의존하지 않는다. 기존 import 경계 검사를 완화하지 않는다. #218 역시 이 커스텀 연결 계약을 소비할 수 있으며, 지금 이야기형 전용 API나 범용 플러그인 구조를 추가하지 않는다.

첫날 밤 화면은 실제 replay의 `currentStep`, `availableActions`, 필수 준비 및 후속 공개 상태를 기존 사용자 흐름에 연결한다. 내부 occurrence 하나마다 별도 사용자 step이나 행동 탭을 만드는 것을 뜻하지 않으며 7.4절의 단일 직업 단계/자유 행동 경로를 따른다. UI가 캐릭터 이름만으로 행동을 추측하거나 `firstNightOrder`를 roster로 단순 필터링하여 런타임 순서를 대신하지 않는다. 여러 소유자·획득 능력·재준비는 런타임 occurrence와 출처를 유지해 서로 구별한다.

사용자가 선택할 수 있는 대상·정보·보류·선택적 행동은 기존 custom 계약의 입력·후보·결과 형태로 연결한다. 같은 종류의 정보 선택·플레이어 선택·공개·저장 실패는 공통 흐름으로 처리하며, 캐릭터별 규칙 예외를 화면에 중복 구현하지 않는다. Core가 거부한 명령은 상태·이벤트·저장에 부분 반영하지 않는다. 질의와 제안만으로 확정 기록이나 진행 위치를 바꾸지 않는다.

공개 화면은 custom이 제공한 공개 전용 payload만 받는다. 전체 replay 상태, 비공개 계산 근거, 숨은 역할 및 다른 플레이어의 정보를 부수적으로 전달하지 않는다. 다시 보기는 확정 당시 정보를 사용하고 이벤트를 추가하지 않는다. 탭 이동은 현재 확정 진행·입력 맥락을 유지하고, 화면 이동 자체로 행동을 확정하지 않는다.

공식·커스텀 타입·검증기·WASM·저장 책임의 분리를 유지한다. 시나리오 JSON의 기존 파일 형식 버전은 유지하되, 이번 연결을 이유로 시나리오 revision·ruleset version이나 과거 게임 migration을 추가하지 않는다.

외부 공식 custom-script JSON 호환, 이후 밤 UI·실행, 새 캐릭터 능력·활성화 정책, BMR·Homebrew·온라인 공유, 공식 페이지 재설계, 앱 내부 시나리오 보관, #218 이야기형 마도서 테마는 제외한다. 승인된 시각·상호작용의 실질적 변경이 필요하면 기존 승인으로 간주하지 않는다.

### 7.1. 기존 UI 재사용과 내부 구조 재설계의 경계 — 2026-09-11 승인 보완

사용자가 기존 공식 마도서의 단계별 구현을 그대로 연결하기 어렵다는 점을 확인하고, 제시한 책임 분리 방향을 spec·plan에 반영하여 이슈에 기록하도록 요청했다. **기존 UI 재사용은 기존 내부 구조의 보존을 뜻하지 않는다.** 유지할 것은 사용자에게 보이는 배치·세부 테마·정보 위계와 입력·대상 선택·공개·기록의 동작이다. 이를 충족하기 위해 컴포넌트 분리, 상태 흐름과 연결 계층의 재설계를 허용한다. 내부 구조 변경을 이유로 승인된 UI를 범용 폼이나 별도 동선으로 대체하지 않는다.

책임은 다음과 같이 분리한다.

| 경계 | 소유하는 판단 | 맡지 않는 판단 |
| --- | --- | --- |
| 시나리오 definition | 정규 첫날 밤 행동의 명시적 순서 | 실행 중 별도 순서 사본·화면 단계 번호 |
| custom Core | 실제 배역/효과에 따른 실행 가능 여부, 순서와 준비·후속 관계, 허용 입력·결과, occurrence별 확정과 replay | 테마·DOM·탭·입력 폼의 배치 |
| custom 세션/controller | 현재 입력, 선택 왕복, 제안·확정·공개 문맥, 자동 저장과 최신성 | 공식 시나리오 순서의 복제·캐릭터 규칙의 재계산 |
| UI 연결 계층 | Core의 행동/입력/공개를 기존 UI의 값·선택지·동작에 대응 | 자체적인 다음 단계 결정·없는 행동 생성·입력 계약 추측 |
| 공용 표현 | 기존 마도서의 세부 표현과 접근성·조작 방식 | runtime DTO·명령·저장·순서 정책 |

공식 UI에 있던 고정 단계 ID, 스크립트별 실행 순서, 공개 전후 확정 방식의 가정을 custom 진행에 이식하지 않는다. 행동별로 어떤 입력/공개 표현을 쓸지 선택하는 연결은 가능하지만, 그 매핑이 행동의 실행 여부·순서를 결정해서는 안 된다. 화면의 현재 단계와 진행 목록, 선택 가능한 행동은 동일 canonical에서 Core가 제공한 결과를 따른다.

기존 UI에 필요한 정답/등록/허용 후보·고정 후보 등의 정보가 custom 계약에 부족하면, custom Core가 소유하는 읽기 전용 입력·표시 계약을 보완한다. 캐릭터 규칙과 판정은 기존 담당 domain에 남긴다. 공식 DTO로 변환하거나 웹에서 규칙을 복제하여 맞추지 않는다. 같은 입력 종류는 공통 흐름을 사용하고, 지원 행동별 예외를 여러 화면에 중복시키지 않는다. 공식 runtime과 custom runtime은 계속 독립적이다.

새 연결 구조는 승인된 TB/SnV 첫날 밤 범위와 실제 소비자에 필요한 수준으로 제한한다. 범용 플러그인 엔진·새 낮/이후 밤·BMR 규칙을 추가하지 않는다. 공식 화면도 추출한 공용 표현을 사용하되 기존 동작·저장은 유지한다. 파일·모듈·인터페이스와 작업 순서는 plan에서 정한다.

### 7.2. 시나리오 명시 순서와 준비의 연결 — S3 정정

사용자 제공 `clocktower-scenario-test.json`의 순서는 dusk → 하수인 → 악마 → 독살범 → 세레노버스 → 세탁부 → 사서 → 수사관 → 요리사 → 점쟁이 → 첩자 → dawn이다. 실제 참가하지 않거나 현재 규칙상 실행되지 않는 정규 행동은 Core가 제외하되, 적용되는 정규 행동의 상대 순서는 definition을 따른다. 하수인/악마 정보를 앞에 둔 유효한 게임의 배치 완료 후 세탁부 준비가 먼저 나타나서는 안 된다.

‘Core 순서 유지’는 시나리오의 명시 순서와 유효성·인과 관계를 유지한다는 뜻이다. 모든 초기 준비를 먼저 실행하는 현재 구현을 보존한다는 뜻이 아니다. 최초 준비는 관련 행동에 연결하고 무관한 앞선 정규 행동을 가로막지 않는다. 획득·모의·교환에 따른 필수 준비/재준비·통지는 실제 출처와 필요성을 따라 처리하며, UI가 무조건 미루거나 자동 확정하지 않는다. 준비와 전달 사건 및 당시 공개 payload는 구분하여 보존한다.

사용자에게 시나리오 순서를 다시 선택시키거나 배치 전 별도 준비 화면을 추가하지 않는다. 하수인/악마만 항상 첫 화면으로 강제하는 수정도 하지 않는다. 사용자가 다른 유효한 순서를 지정하면 같은 UI가 그 순서대로 동작해야 한다. 이 보완은 기존 시나리오 순서 요구의 이행이며, 이전 A/B 질문은 철회했다.

기존에 유효하게 저장된 초기 준비 선행 기록은 계속 전체 검증·복원할 수 있어야 한다. 사건을 삭제·재정렬하거나 기존 공개 snapshot을 새 준비 시점으로 바꾸지 않는다. 잘못된 순서·출처·입력의 기록을 호환 명목으로 허용하지 않는다. 새 실행 흐름과 이전 기록 보존을 함께 만족해야 하며, 파일 버전·이벤트·Undo 단위는 유지한다.

### 7.4. 기존 UI/UX 복원과 새 UI 사전 승인 — 2026-09-11 사용자 지시

사용자가 실제 플레이에서 공개 형식, 자유 행동 탭, 선택 강조/결과/복귀, 세레노버스·세탁부의 직업별 진행 차이를 지적했다. 이후 “세탁부/세탁부 준비처럼 UI상 step이 나뉘지 않았다”, “전체적으로 다시 한번 BMR 마도서와 비교”, “임의로 UI 만들기 전에 꼭 확인받고 spec에도 반영”을 명시했다. 아래는 그 지시의 요구사항 기록이며, 전체 후속 구현 계획을 승인했다는 뜻이 아니다.

1. **재사용 단위는 실제 사용자 화면과 상태 전환이다.** shell/색상/컴포넌트 이름만 공유하거나 기존 UI를 참고해 새 폼을 만드는 것은 충족하지 않는다. BMR의 전체 시각·공통 상호작용을 기준으로 삼고, BMR에 없는 TB/SnV 직업의 완성된 입력·결과·공개·통지 표현을 사용한다. 기존 BMR 승인에서 제외된 진행 결과 카드·별도 단계를 되살리지 않는다. 현재 할 일의 직업 아이콘/정체 클릭은 원본의 직업 설명 조회를 제공한다(후속 사용자 인수 지적 반영). 직업 탭/좌석의 승인된 상세 조회는 유지한다.
2. **직업 준비를 새 사용자 단계로 노출하지 않는다.** 세탁부/사서/수사관의 준비와 전달은 같은 능력 사용의 한 직업 카드·목록 행 안에서 기존 선택·편집·공개 흐름으로 처리한다. 별도 `… 준비` 행/탭/추가 확인 버튼을 넣지 않는다. Core 사건·규칙·출처·Undo/과거 공개를 합치거나 자동 생략하는 요구가 아니다. 다른 owner·획득·모의 능력은 이름이 같아도 별개로 유지한다.
3. **입력 위치와 완료 동선도 보존한다.** 실제 TB 세탁부는 마도서에서 두 대상을 수락한 뒤 진행에서 보여줄 캐릭터를 고른다. direct action은 원본에 있는 마도서 결과/다음 동선을 유지하고, 정보 선택·세레노버스 통지는 각각 기존 경로를 사용한다. 모든 행동에 같은 확인/수정/다음 UI를 붙이지 않는다. 선택된 좌석의 상태/강조/잠금/대상·결과 정보도 같은 표현을 사용한다.
4. **자유 행동은 기존 dock/패널로 제공한다.** `변종 처형 판단`을 정규 순서 위 pill/tab으로 만들지 않는다. 실제 사용 가능 여부는 Core에 따른다. 기존 SnV의 판단 기록·복원도 가져온다([계획 R3](../plans/issue-220-custom-grimoire-plan-v3.md)). custom Core의 명령·이벤트·replay/projection을 보완하고 기존 session/GameFile의 자동 저장·JSON·복원·Undo에 연결한다. UI 전용 임시 판단이나 별도 저장소로 대체하지 않는다. official/custom 분리와 7.1의 책임 배치는 유지한다. 판단 기록을 처형의 새 필수 선행 조건으로 만들지 않는다. 처형 결과 동선의 차이는 원본 대조 후 구체화하며 새 UI는 사전 승인을 받는다.
5. **공개 콘텐츠와 후속 안내를 직업별로 재사용한다.** 기존 제목/수신자 안내/좌석·직업 카드/숫자·단위/문구/닫기 의미를 BMR 테마로 연결한다. payload에 값이 더 있다는 이유로 표시를 늘리거나 custom 문자열 나열로 바꾸지 않는다. 공개 중 비공개 화면 격리와 과거 snapshot은 유지한다.
6. **새 UI는 반드시 사용자 사전 승인을 받는다.** 기존에 없는 화면·탭·패널·선택지·필드·버튼·설명 문구·입력 위치·상태 전환이 필요하면 원본과 차이, 필요한 이유, 구체적 제안, 데이터/진행 영향을 먼저 제시한다. 명시적인 승인 전 제품 코드에 구현하지 않는다. ‘내부 구조 재설계 승인’, ‘계획 전체 구현’, ‘대표 프로토타입 승인’을 미제시 UI의 포괄 승인으로 사용하지 않는다. 같은 UI를 유지하는 컴포넌트 추출·버그 수정·기존 승인 복구에는 반복 승인을 요구하지 않는다.
7. **범위 전체를 대조한다.** 직업/배치/마도서/진행/공개/상세/utility/기록/dialog의 상태와 등록 행동 29개를 원본 대응표로 추적한다. 적용 여부·원본·실제 확인·남은 공백을 구분한다. 대표 두 직업, BMR CSS import, 기능 테스트 통과로 전체 UI 재사용을 완료 처리하지 않는다.

추가 수용 조건은 V01–V08이다. 기존 63개와 합쳐 71개로 추적한다. R3의 판단 기록·복원은 포함하며, 기존 파일·과거 이벤트의 호환성을 보존한다.

### 12. S1 — 자동 저장 대체 정책 (승인 완료)

사용자 결정: 자동 저장은 최신 게임 진행을 보관하는 용도다. 새 게임 또는 사용자가 이어 쓰기로 선택한 게임을 저장할 때 이전 자동 저장을 별도 질문 없이 대체한다. 이전 게임을 보관하려면 사용자가 게임 JSON으로 별도 내보낸다.

**시나리오당 슬롯 하나를 유지하며, 교체 확인·자동 백업·여러 게임 선택 목록을 추가하지 않는다.**

- `새 마도서 쓰기`는 확인 없이 설정으로 이동한다. 설정 편집만으로 기존 자동 저장을 변경하지 않는다.
- `게임 설정 확정`에서 유효한 새 게임을 생성하고 저장하면 같은 시나리오의 기존 자동 저장을 즉시 대체한다. 기존 게임 유무에 따른 교체 대화상자나 JSON 내보내기 의무 단계를 두지 않는다.
- GameFile은 검증·최종 검토만으로 자동 저장을 대체하지 않는다. 사용자가 `마도서 이어 쓰기`를 선택하면 전체 검증·replay를 통과한 그 게임을 재개하고 해당 슬롯에 자동 저장한다. 다른 게임 또는 다른 시점의 기록이 있어도 교체 확인을 묻지 않는다.
- 기존 슬롯이 손상됐더라도 유효한 새 게임 시작이나 유효한 파일 재개로 저장할 때는 확인 없이 대체한다. 읽기·replay 실패만으로 빈 게임을 만들지는 않는다. 읽기/권한 오류는 손상으로 단정하지 않고 오류 표시·재시도를 제공한다.
- 검증 또는 저장 실패는 성공으로 처리하지 않는다. 기존 데이터를 먼저 삭제한 뒤 쓰지 않으며, 실패 시 이전 저장은 보존하고 현재 상태의 재시도를 제공한다. 재시도는 이미 수락된 이벤트를 중복 실행하지 않는다.
- 게임 전환 뒤 이전 게임의 늦은 자동 저장 요청이 새 게임을 다시 덮어쓰지 않게 한다. 현재 선택한 게임의 저장이 최종 상태가 되어야 한다.
- 앱은 대체된 이전 게임의 별도 사본을 보장하지 않는다. 사용자가 미리 내보낸 JSON 파일은 영향을 받지 않는다.

| ID | 상황·조작 | 기대 결과 |
| --- | --- | --- |
| S1-a | 기존 게임이 있는 시나리오에서 새 마도서 쓰기 → 설정 편집 | 확인 없이 설정 진입, 기존 저장 불변 |
| S1-b | 위 설정에서 유효한 게임 설정 확정 | 교체 확인 없이 새 게임 시작·자동 저장 시도. JSON 내보내기 의무 단계 없음 |
| S1-c | 새 Setup 검증 또는 저장 실패 | 기존 저장 보존, 원인 표시·재시도. 이전 게임 선삭제·새 게임 성공 오표시·중복 이벤트 없음 |

## 2026-09-11 인수 피드백 — 기존 UI 재사용 보정

사용자가 모바일 캐릭터 목록의 과밀/잘림, SnV와 다른 플레이어·인원 구성·완료 버튼, 정원 초과 선택, 임의 배치 UI를 지적하고 BMR UI도 가져오도록 요청했다. 기존 구성 승인은 임의의 세부 UI 변경 승인이 아니다.

- 작성 2단계: 작은 화면에서 직업 이름을 자르지 않고 읽을 수 있게 열 수·간격·줄바꿈을 조정한다.
- 직업 설정: SnV Production의 플레이어 수·분포 카드, 직업 설명과 확정 액션을 공통 컴포넌트로 재사용한다. 현재 Core 분포가 찬 종류는 추가 선택을 막으며, 분포 조회 중 오래된 한도로 추가 선택하지 않는다. 인원/보정 변경 후 정원에 맞지 않는 뒤쪽 선택을 정리한다.
- 배치·상세: BMR Production의 실제 배치 컴포넌트와 플레이어 상세를 재사용한다. 무작위 배치·초기화·좌석/토큰 선택·좌석 이름·하단 선택판·좌석 확정 동선을 사용한다. 주정뱅이의 표시 배역은 custom Core가 허용하는 후보를 전달한다.
- UI 재사용은 커스텀 Core/저장 경계를 바꾸거나 BMR 캐릭터 규칙을 새로 지원하는 작업이 아니다. 첫날 밤/자동 저장의 승인 계약은 유지한다.


### 추가 인수 보정: 유틸리티와 진행 화면 (2026-09-11)

상단 SnV 유틸리티(새 게임·저장/불러오기·버그 제보)와 진행 탭의 실제 공통 UI를 연결한다. 악의 팀 정보는 SnV의 현재 컴포넌트, 일반 행동 카드/반응형 2열 배치는 BMR 공통 구조를 사용한다. 현재 직업/플레이어/능력/준비 상태, 공개 행동, 밤 순서와 기록에 접근할 수 있어야 한다. 새 게임 진입·JSON 검토만으로 자동 저장을 바꾸지 않는 S1 계약을 그대로 따른다. 제보 미리보기는 기본으로 이름과 메모를 제거하고 원본 포함은 명시적 선택으로 한다. 이 보정은 기존 마도서 재사용에 대한 인수 피드백이며 커스텀 Core 규칙이나 첫날 밤 범위를 확장하지 않는다.

### BMR 전체 테마 통일 (2026-09-11)

사용자 요청: “직업/진행/마도서 등 모든 부분 세부 테마 같은 것도 bmr 마도서로 다 맞춰줘. snv 테마 남기지 말고.”

커스텀 마도서 진입 이후 전체 화면(직업·배치·진행·기록·저장·제보·플레이어/직업 상세·플레이어 공개·낮 복원·로딩/오류)을 BMR의 붉은 밤/혈월, 따뜻한 낮/해, 금색 행동 강조로 통일한다. 공통 레이아웃을 쓰더라도 SnV 보라색 테마를 상속하지 않는다. 공식 캐릭터 아이콘과 종류/진영 구분 색은 해당 데이터의 의미대로 유지한다. 기능·첫날 밤 범위·자동 저장 규칙은 바꾸지 않는다.

### 진행 순서 간소화 (2026-09-11)

TB 마도서의 표시 방식을 참고해 진행 목록은 상태와 직업명 중심으로 구성한다. 좌석·이름·일반 행동 설명은 목록에서 반복하지 않고 현재 행동 카드에 표시한다. 획득/표시 능력의 정체 관계는 짧게 유지한다. 준비/전달 canonical 사건은 보존하되 동일 능력 사용은 하나의 직업 행으로 연결하며 별도 준비 행을 만들지 않는다. 서로 다른 소유자/출처는 구별한다. 선택적 자유 행동은 기존 dock으로 제공하고 진행 목록 위에 별도 탭을 추가하지 않는다. 색상과 나머지 마도서 테마는 BMR을 유지한다.


### 기존 마도서 동작 연결 — 수정 계획 v2의 승인 보완 (2026-09-11)

전체 수정 계획 검토 뒤 사용자는 진행 중 배치 복귀(R2)를 “하는 게 맞지. 계획에 반영해”, 직업 확정 유지(R1)를 “그것도 승인할게”로 승인했다. 구현 기준은 [수정 계획 v2](../plans/issue-220-custom-grimoire-plan-v2.md)이며, 아래 동작과 수용 조건은 앞선 일반적인 UI 재사용 문구를 구체화한다. 구현·인수 완료를 뜻하지 않는다.

- 직업 확정 뒤에는 인원·악마·배역 구성의 확정을 유지한다. 탭 이동, 좌석 화면의 뒤로 가기, 직업 설명 열기로 확정을 풀지 않는다. 배역 구성 변경은 새 게임에서 한다. 선택 여부·악마·정원 제한과 관계없이 설명을 조회할 수 있다.
- 진행 중 `배치로 돌아가기`는 진행 초기화 확인 후 게임 시작 당시 설정의 인원·이름·배역·Shown·좌석을 채운 배치 화면으로 돌아간다. 확정된 배역을 재배치하고 이름·허용 Shown을 수정할 수 있다. 진행 중 교환·획득·중독·사망은 새 게임에 복사하지 않는다.
- 복귀 확인 취소는 현재 입력·진행을 보존한다. 배치 편집만으로 자동 저장을 바꾸지 않는다. 새 좌석 확정과 저장 성공 시 같은 시나리오의 새 게임으로 첫날 밤부터 시작하며, 실패는 기존 저장 보존·수락된 Setup의 저장 재시도로 처리한다. 새 확정 전 reload는 기존 저장 게임을 복원한다.
- 상단 `새 게임`은 현재 작업 초기화를 확인한 뒤 빈 설정으로 이동한다. 최종 검토의 `새 마도서 쓰기`와 자동 저장의 교체에는 확인을 추가하지 않는다. S1의 단일 슬롯·원자적 대체·이전 writer 차단을 유지한다.
- 대상 선택은 기존 마도서 좌석과 선택 패널에서 수행한다. 진행에는 필요한 정보 입력과 공개·확정 동작을 둔다. 단순 탭/상세/저장 조회는 현재 입력과 확정 대기 제안을 보존하며, 확정·Undo·다른 행동 선택으로 맥락이 바뀌면 이전 입력을 폐기한다.
- 기록은 저장/불러오기 유틸리티의 최신순 목록에서 연다. 과거 공개와 현재 제안의 공개 상태를 분리하며, 과거 조회로 현재 제안을 지우거나 새 사건을 만들지 않는다. 첩자 공개는 당시 payload를 기존 마도서 좌석 형태로 표시한다.
- 기존 custom 사실을 보여주는 표식과 Core 경고를 기존 공용 표현에 연결하고 의미 없는 생존 칩을 제거한다. 이를 위한 읽기 전용 replay projection 확장은 custom 도메인이 소유하며, 파일 버전·명령·이벤트·캐릭터 규칙·Undo 단위와 공식/커스텀 경계는 유지한다. 초기 준비의 실행 연결은 7.2절의 시나리오 순서 계약을 따른다. 수동 메모/토큰 저장 명령이나 일반 무작위 규칙 추천 API는 추가하지 않는다.
- BMR의 밤/낮 테마와 기존 직업·정보·마도서·확인·공개·유틸리티의 세부 동작을 사용한다. 경과 시간은 마도서와 진행이 같은 값을 표시하고 탭 이동에 유지하며, 기존처럼 reload부터 새로 측정한다. 첫날 밤의 도착점은 Day 또는 게임 종료다.

### V05 후속 결정 — 처형 확인 문구 (2026-09-11)

사용자가 기존 첫 문장만 사용하는 안을 승인했다. custom 처형 확인창은 원본 모양과 버튼을 공유하고 `처형을 확정하면 현재 진행이 중단됩니다.`를 표시한다. custom의 같은 확정에서 처리되는 사망 결과와 충돌하는 원본 뒷문장은 사용하지 않는다. official SnV 동작과 문구는 변경하지 않는다. 판단 기록은 custom Core의 기존 확정 이벤트·session 저장·복원·Undo 책임 안에서 처리한다.

### 후속 인수 지적 — 현재 할 일 및 선택/공개 UI

사용자가 현재 할 일의 직업 아이콘 설명 조회 누락을 지적했다. 기존의 ‘진행 직업 상세 진입 제외’ 해석을 철회하고 원본의 클릭 설명 조회를 복원한다. 단순 선택 수락 후 진행 복귀에 임의 다음 버튼을 끼우지 않는다. 원본 직업별 필수 공개/통지와 대상 수락을 구분한다. 대상 선택 전 세탁부의 비활성 정보 입력/공개 폼을 미리 노출하지 않는다. 데스크톱 선택 패널 위치, 좌석 강조, 공개 레이아웃, 중독/취함의 불필요한 선택지는 실제 원본 상태 대조로 검증한다.

### 추가 인수 기준 T10 — 2026-09-11

- 중독/취함 세탁부·사서·수사관은 기존 TB처럼 두 대상과 전달할 직업을 입력하며, 별도 ‘정답 플레이어’ 선택을 사용자에게 요구하지 않는다. Core 내부 준비 사실과 공개 정보·등록 출처를 보존할 책임은 유지한다.
- 두 명 선택은 완성된 유효 조합이 될 때 원본의 완료 강조/흐림을 적용한다. 부분 선택과 최종 수락 모두 유효한 정보로 완성할 수 있는 Core 후보를 기준으로 하며, 불가능한 조합으로 진행 탭에 복귀하지 않는다.
- 같은 표시 직업이 실제 직업/주정뱅이/획득 능력에 함께 있을 때 각 소유자의 선택·입력·공개를 하나의 사용자 흐름으로 유지한다. 별도 준비 행을 숨기는 것만으로 충족하지 않는다. 소유자와 ability/occurrence 출처, 시나리오 순서의 기존 계약을 보존한다.
- 은둔자/첩자 취급은 관련 정보 직업 전체에서 원본의 행동별 판정 단위를 따른다. 선/악 또는 악마 여부 판정에 전체 직업 목록을 별도 등록 UI로 노출하지 않는다. 실제 직업 정보를 전달하는 원본 캐릭터 선택과 구별한다.
- Undo는 내부 식별자가 아닌 사용자용 행동 요약을 표시한다. 되돌리기 단위와 저장 구조는 변경하지 않는다.
- 악마 공개, 붉은 청어 지정과 점쟁이 판정, 첩자 공개까지 기존 BMR/TB 상태별 표현을 대조한다. 외곽 컴포넌트 공유만으로 내부 좌석·토큰·아이콘·크기·선택 완료 동작을 대체하지 않는다. 새 UI는 기존 승인 규칙을 따른다.

### T10 구현 중 원본 대조 및 사용자 표기 확정

- 판정 입력 제목은 ‘이번 판정의 XXX 취급’이다. ‘실제 정체/악’처럼 실제 판정값이 감춰지는 항목을 만들지 않는다. 선/악 판정은 실제 값 ‘선/악’을 표시하며, 사용자 지시는 버튼 순서 변경이 아니다. 시계공의 종류 판정도 ‘외지인/하수인/악마’ 등 해당 실제 값을 표시한다. 이 입력은 Core가 제공한 해당 판정의 후보에만 대응한다.
- 재봉사는 취급을 선택하면 Core 결과를 표시한다. 취급 선택과 전달 결과 선택을 중복 요구하지 않는다. 중독·취함·보르톡스 등 재량 전달은 기존 별도 계약을 유지한다.
- 첩자 원본 기준은 TB의 실제 production 호출 경로(`main.tsx` → `TroubleBrewingLiveFlow` → 잠긴 `TroubleBrewingLiveGrimoire`)이다. 이전 `revealMode` 전용 화면을 실제 원본으로 잘못 본 기준을 정정한다. 마도서 shell과 비활성 메뉴, 원본 중앙 ‘확인 완료’, 좌석별 토큰 상세 열람을 유지한다. 읽기 전용은 편집 금지를 뜻하며, 허용된 공개 토큰의 열람을 막는 뜻이 아니다. 공개는 allowlisted payload의 정체·상태·토큰만 사용하며 현재 메모나 파일의 비공개 내용을 추가하지 않는다.

### T11 직업 설정의 인원 보정 표시 — 2026-09-11 승인

사용자가 제시된 전체 명세와 수용 사례에 ‘추가해’로 승인했다. 현재 Core는 비고르모르티스·팡 구·남작의 인원 보정을 이미 계산하지만 커스텀 직업 설정에는 원인 표시가 빠져 있다. 아래는 계산 규칙 추가가 아니라 승인된 보정 표시의 명세다.

1. 실제 선택한 배역에 인원 보정 직업이 있으면 BMR의 보정 영역과 반응형 배치를 재사용하여 직업명과 보정 내용을 표시한다. 시나리오 후보에만 포함된 직업은 적용 대상으로 표시하지 않는다. 데스크톱은 악마 선택과 적용 인원 구성 사이, 모바일은 BMR 하단 직업 설명 영역의 압축 표시를 기준으로 한다.
2. 비고르모르티스는 외지인 −1·주민 +1, 팡 구는 외지인 +1·주민 −1, 남작은 외지인 +2·주민 −2를 표시한다. 자동 보정에 선택 버튼이나 추가 확인 절차를 만들지 않는다. BMR 대부의 선택 가능한 보정 규칙을 커스텀에 추가하지 않는다.
3. 여러 보정이 함께 적용되면 각 직업의 보정을 구분하여 표시하고 ‘적용 인원 구성’에는 Core가 계산한 최종 인원을 표시한다. 외지인 0명 등 한계로 실제 변화가 제한되면 그 사실을 함께 표시하여 감소가 적용된 것으로 오인하지 않게 한다. 개별 직업의 규칙상 보정과 합산 후 실제 적용량을 구분하고 임의로 특정 직업에 제한분을 배분하지 않는다.
4. 인원·악마·배역 변경 시 보정 표시와 최종 구성은 같은 계산 결과로 갱신한다. 조회 중이거나 실패한 경우 이전 보정을 현재 결과처럼 표시하지 않는다. 기존 선택 제한과 오류 복구 동작을 유지한다.
5. 직업 확정 후와 저장·복원 후에도 원래 게임 설정의 보정을 조회할 수 있다. 진행 중 정체 변경으로 초기 인원 보정 표시가 바뀌지 않는다.
6. 보정 원인·합산·제한·최종 구성은 커스텀 Core가 제공하고 UI는 BMR 표현으로 표시한다. 웹에 별도 보정 규칙을 복제하지 않는다. 기존 저장 구조와 게임 규칙은 유지한다.

### 배치 복귀 표시 범위 정정 — 2026-09-12

사용자 정정: 진행 중 일반 마도서 탭에는 기존 `배치로 돌아가기`를 표시한다. 마도서 선택 행동(선택 및 결과/통지 연결)이 진행 중일 때만 숨긴다. 기존 BMR 초기화 확인창과 `restartFromSetup()` 경로를 재사용하고, 취소·기존 저장 보존 계약은 유지한다. 전체 진행 중 제거라는 이전 기록을 대체한다.


### 취한 시계공 입력 보완 — 2026-09-12

첨부 `test0912-game-3.json`의 철학자 영향으로 취한 시계공에 원본 숫자 입력 UI를 연결한다. Core가 유한 후보로 제공하더라도 숫자 버튼을 나열하지 않고 입력값을 해당 Core 후보와 대조한다. 이 정보 전달에는 불필요한 은둔자 취급 UI를 표시하지 않는다. 일반 취급 UI의 잔존 `실제 정체` 문구도 실제 진영/종류 값과 `이번 판정의 XXX 취급` 제목으로 교체한다. Core 규칙·허용 범위·저장 형식은 변경하지 않는다.


### Undo 확인창 정정 — 2026-09-12

사용자 정정에 따라 OS 기본 confirm을 제거하고 기존 앱 내 `LiveUndoDialog`를 재사용한다. Core의 최신 Undo 단위에 포함되는 사건을 사람용 요약으로 표시하며 취소/되돌리기를 제공한다. 원본 레이아웃에 BMR 색상을 적용한다. 확인창을 연 뒤 게임 상태가 바뀌면 이전 요청을 실행하지 않는다. 기존 native confirm을 요구하던 T13 문구와 테스트를 대체하며 action 의존/Undo 경계는 변경하지 않는다.
