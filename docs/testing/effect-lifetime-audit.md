# 직업 변경과 지속 효과 수명 조사 — 2026-09-26

기준: `origin/develop`의 `741c36922a293f35410cd5b67c1129560e8fe9ce` (PR #267 병합 후).
조사 브랜치: `codex/audit-effect-lifetimes`.
추적 이슈: [#269](https://github.com/metishonora/clocktower/issues/269).
이 문서의 조사 결과와 아래 진단 로그는 위 기준 커밋에서 얻었다. 후속 구현 결과는 마지막 절을 참고한다.

## 결론

직업 변경 후 상태가 남는 문제가 더 있다. 뱀조련사·사랑꾼은 실제 판정 오류이고,
공식 스크립트 엔진의 세레노버스에는 이전 지정이 재활성화되는 오류가 있다.
커스텀 엔진의 마녀·세레노버스·집사는 실제 효력이 종료돼도 자동 표식이 활성처럼 남는다.

전체 엔진 교체는 필요하지 않다. 이미 존재하는 능력 인스턴스와 출처 추적을 활용해
**효과를 처음 만든 기록과 현재 효과를 유지하는 능력을 구분하고, 종료·일시 중단 조건을
명시하는 구조 보강**이 필요하다. 직업 변경 때 해당 플레이어의 상태를 모두 지우면
다른 사람이 건 취함·중독까지 사라지는 새로운 오류가 생긴다.

## 규칙 기준

- 능력을 잃거나 다른 직업이 되면 그 능력의 지속 효과가 끝난다. 사망 후 작동하는
  능력도 취함·중독에는 영향을 받는다. [공식 Abilities](https://wiki.bloodontheclocktower.com/Abilities)
- 취함·중독의 대상은 플레이어다. 다른 사람이 유지하는 효과는 대상의 직업 변경만으로
  사라지지 않는다. 일시적인 능력 무효와 영구적인 능력 교체를 구분해야 한다.
  [공식 States](https://wiki.bloodontheclocktower.com/States)
- 사랑꾼은 사망 후에도 능력이 작동한다. 이는 직업을 잃은 후까지 무조건 유지한다는
  뜻이 아니다. [공식 Sweetheart](https://wiki.bloodontheclocktower.com/Sweetheart)
- 세레노버스의 집착 위반 처형은 공식 안내상 다음 낮이나 밤에도 가능하다. 이전 직업 인스턴스의 지정을
  새 세레노버스의 지정으로 취급하면 안 된다.
  [공식 Cerenovus](https://wiki.bloodontheclocktower.com/Cerenovus)

뱀조련사는 교환 직후 새 뱀조련사의 자기 중독을 유지해야 한다. 위 일반 규칙을 이
상호작용에 적용하면, 새 뱀조련사가 다른 직업으로 바뀔 때 중독은 끝난다. 성공한 교환
당시의 원래 뱀조련사는 이미 악마가 됐으므로, 그 옛 능력을 유지 조건으로 삼아서도 안 된다.
캐릭터 설명의 '영구'와 저장 형식의 `never`를 능력 교체와 무관한 효과로 해석한 것이 잘못이었다.

## 재현한 결함

| 구분 | 경로 | 기대 동작 | 현재 동작 | 확인 범위 |
| --- | --- | --- | --- | --- |
| 뱀조련사 중독 | 교환 후 새 뱀조련사를 마귀할멈이 다른 직업으로 변경 | 자기 중독 종료 | 새 직업도 계속 중독 | 커스텀·공식 JSON 명령/재생 |
| 뱀조련사 중독 | 새 뱀조련사를 이발사가 다른 사람과 교환 | 이전 자기 중독 종료 | 이전 플레이어의 새 직업에 중독 잔존 | 커스텀 JSON 명령/재생 |
| 사랑꾼 취함 | 사랑꾼 사망으로 취함 생성 → 죽은 사랑꾼을 다른 직업으로 변경 | 대상의 취함 종료 | 대상이 계속 취함 | 커스텀 낮·밤 사망, 공식 밤 사망 |
| 세레노버스 지정 재활성화 | 지정 → 마귀할멈이 화가로 변경 → 다음 밤 다시 세레노버스로 변경 | 옛 지정은 종료된 상태 유지 | 옛 지정이 `sourceEffective: true`, `canExecute: true`로 복귀 | 공식 JSON 명령/재생 |
| 저주·집착·주인 표식 | 마녀·세레노버스·집사가 지정 후 다른 직업으로 변경 | 종료된 능력의 표식 제거 | `cursed`·`mad`·`master` 자동 표식 잔존, 비활성 사유도 없음 | 커스텀 JSON 명령/재생 및 UI 데이터 경로 확인 |

집사 재현은 커스텀 시나리오의 허용된 밤 순서를 집사 → 마귀할멈으로 배치했다.
새 밤 기록이 없는 상태에서 순서를 설정한 뒤 정상 명령으로 진행했다.
표식 문제는 이번에 브라우저를 실행한 결과가 아니라, 실제 재생 응답과 그 응답을 그대로
표시하는 `customPlayerTokens` / `playerTokenPresentation` 경로로 확인한 것이다.

같은 원인의 인접 문제도 확인했다. **이미 취함을 발생시킨 죽은 사랑꾼이 이후 중독돼도
취함이 일시 중단되지 않는다.** 이 한 항목은 공개 명령 시나리오가 아닌, 유효한 효과와
외부 중독을 넣은 제한된 내부 상태 검사로 재현했다. 생전 중독된 채 죽어 처음부터
효과가 발생하지 않는 경우와는 다른 문제다.

## 원인

### 1. '기한 없음'을 '유지 조건 없음'으로 처리

커스텀 `effects.rs::resolve_effects`는 `durable_impairments`의 모든 항목을
`requires_source: false`로 평가한다. 여기에 뱀조련사와 사랑꾼이 들어간다.
능력 교체, 능력 비활성, 사망 후 능력 유지 예외를 확인하지 않는 우회 경로다.

- [effects.rs](../../crates/custom-domain/src/effects.rs): 후보 생성과 유효성 반복 계산
- [state.rs](../../crates/custom-domain/src/state.rs): `DurableImpairment`
- [sects_and_violets.rs](../../crates/custom-domain/src/characters/sects_and_violets.rs): 뱀조련사 교환, 낮·밤 사랑꾼 후속 효과

공식 엔진도 별개 구현에 같은 문제가 있다. `active_snake_charmer_impairments`와
`base_snv_impairments`는 과거의 성공한 교환·취함 이벤트를 모두 모으고, 현재 유지 조건을
대조하지 않는다. [공식 SnV 구현](../../crates/domain/src/characters/sects_and_violets.rs)

### 2. 발생 출처와 유지 주체가 한 필드에 섞임

`DurableImpairment.source_ability_use`는 효과를 만든 행동의 출처다.
`reducer.rs::apply_snv_facts`는 이 값이 원래 행동의 능력과 같아야 한다고 검증한다.
뱀조련사에서는 이 출처와 자기 중독을 유지하는 새 뱀조련사의 인스턴스가 다르다.
따라서 `requires_source`만 `true`로 바꾸면 성공한 교환 직후 중독이 사라지는 역방향 버그가 생긴다.
사랑꾼 역시 일반 `effective()`의 생존 조건을 그대로 적용하면 사망 순간부터 취함이 사라진다.

직업 변경 자체는 새 `AbilityInstanceId`를 만들고 과거 출처를 보존하고 있다.
부족한 곳은 변경 처리기가 아니라 그 인스턴스를 효과의 수명과 연결하는 평가다.
[reducer.rs](../../crates/custom-domain/src/reducer.rs)

### 3. 일부 경로는 현재 직업 이름만 확인

공식 `madness_assignments`는 플레이어별 마지막 세레노버스 지정을 가져오고,
현재 직업이 세레노버스인지 확인한다. 지정 당시의 정확한 능력 인스턴스와 해당 밤·낮의
수명 확인이 빠져 있다. 그래서 다른 직업을 거쳐 돌아오면 과거 지정이 되살아난다.
커스텀 판정은 인스턴스와 날짜를 확인하므로 이 검사에서 정상 동작했다.

### 4. 실제 효력과 자동 표식의 수명 판단이 갈라짐

커스텀 `refresh_assignments`는 마녀·세레노버스의 효력을 종료한다. 하지만
`witch_reminders`, `cerenovus_reminders`, `butler_reminders`는 과거 출처와 날짜만 맞으면
표식을 만든다. 표식 디스패처에는 과거 능력도 들어오므로 현재 능력 확인을 생략하면 잔존한다.
생성된 표식에는 `inactiveReason`도 없어 UI에서 활성처럼 보인다.
[reminders.rs](../../crates/custom-domain/src/reminders.rs),
[TB 표식 구현](../../crates/custom-domain/src/characters/trouble_brewing.rs),
[UI 변환](../../web/src/grimoire-custom/customPlayerPresentation.ts)

표식 경로를 조사했으며, 미구현 캐릭터의 효과까지 검증한 결과는 아니다.

## 권장 구조 변경

1. 효과에 **발생 출처**와 **유지 능력 인스턴스**를 별도로 표현한다.
   뱀조련사 중독은 교환 기록을 출처로 보존하면서 새 뱀조련사의 인스턴스에 수명을 묶는다.
   사랑꾼은 실제 발동한 사랑꾼 능력에 묶고 사망 후 유지 예외를 명시한다.
2. 시간 기한, 발동 당시 유효성, 원천 소유권, 현재 가용성, 사망 예외, 자기 중독 예외를
   별도 조건으로 평가한다. 원천 교체로 종료된 효과와 잠시 중단된 효과를 구분한다.
   이미 실패한 발동이 나중에 건강해졌다는 이유로 새로 발생해서는 안 된다.
3. 실제 판정과 자동 표식이 같은 평가 결과를 사용하게 한다. 영구 종료된 표식은 제거하고,
   일시 중단 상태를 남기는 경우 기존 `inactiveReason`으로 표현한다.
4. 공식 세레노버스도 정확한 능력 인스턴스와 시간 창을 확인한다. 직업 이름이 같다는
   이유만으로 과거 지정이나 과거 위반 판정을 새 능력에 승계하지 않는다.
5. 캐릭터별 예외는 각 `characters/<script>.rs`에서 선언하고, 공통 효과 평가기가 적용한다.
   기존 `current_ability_instance`, 출처 장부, 설교자·과학자의 수명 구분을 재사용한다.
   공식·커스텀 엔진의 분리 원칙은 유지하고, 동일한 의미의 회귀 시나리오로 양쪽을 검증한다.

직업 변경 처리기에 `모든 상태 삭제`를 넣거나, 화면에서 캐릭터별로 표식을 숨기는 수정은
권장하지 않는다. 외부 효과, 사망 기록, 이미 전달한 정보와 Undo 근거를 손상시키기 쉽다.
팡 구의 게임 전체 1회 제한과 능력 인스턴스별 사용 기록 같은 차이도 보존해야 한다.
이번 제안은 범용 규칙 언어나 전체 이벤트 스키마 교체가 아닌 효과 수명 모델의 보강이다.

## 기존 보고서·테스트 정정과 저장본 영향

[이전 보고서](vortox-pit-hag-audit.md)의 '뱀조련사의 중독은 직업이 바뀌어도 남는다'는
판정은 잘못됐다. 제공 게임에서는 25번째 이벤트에서 1번이 보르톡스가 될 때 중독이
끝나야 한다. 따라서 이후 거짓 정보 강제가 비활성인 것을 정상이라고 볼 수 없다.
2·3번째 밤 포고꾼의 `false`를 정답으로 판정한 결론도 철회한다.
다른 무효 원인이 없다면 하수인 지목이 없었던 경우 보르톡스 때문에 `true`를 전달해야 한다.

28번째 이벤트에서 임의 사망 대상으로 9번만 선택한 사실, 명시적으로 선택한 보르톡스는
임의 사망 처리로 죽는다는 재현 결과는 별개로 유지된다. 42번째 이벤트의 자기 공격에서
죽지 않은 것을 뱀조련사 중독으로 정당화한 설명은 철회한다.

다음 기존 항목도 수정 시 함께 바꿔야 한다.

- `web/test/custom/vortoxPitHagReportedGame.test.ts`: 직업 변경 후 중독 및 잘못된 정보의 유지 기대값
- `crates/domain/src/tests/issue101_snake_charmer_scenarios.rs`의
  `a_poisoned_character_changed_to_minion_still_counts_for_vigormortis`: 변경 후에도 뱀조련사 중독이 남는다는 기대값
- `issue207_impairments`와 `issue223_reminders`의 인공적인 지속 중독 상태: 실제 유지 인스턴스가 있는 상태로 재작성
- `ARCHITECTURE.md`의 durable poison 설명: 역사적 출처 보존과 현재 유지 조건을 구분하도록 명료화

잘못 확정된 과거 정보·결과를 올바른 규칙으로 재계산하면 엄격한 재생 검증과 충돌할
가능성이 크다. 실제 첫 충돌 이벤트와 복구 정책은 구현 단계에서 검증해야 한다.
익명화한 원본은 오류 재현 자료로 보존하고, 새 규칙의 정상 시나리오는 별도로 생성해야 한다.
이미 전달한 정보나 사망 기록을 몰래 바꾸는 복구를 넣어서는 안 된다.
이 문제는 이전 사랑꾼 `effective: false` 기록 복구 이슈 #268과 원인이 다르며 별도 범위다.

## 재현 자료와 검증

- [진단 패치](effect-lifetimes/probes.patch): 제품 변경 없이 테스트 모듈만 추가한다.
- [커스텀 진단 결과](effect-lifetimes/custom-probes.txt): 12개 중 정상 대조 4개 통과, 결함 재현 8개 실패.
- [공식 엔진 진단 결과](effect-lifetimes/official-probes.txt): 3개 모두 결함 재현으로 실패.
- [기존 테스트 결과](effect-lifetimes/baseline-tests.txt): 커스텀 281개, 공식 381개 통과.

총 15개 진단 함수 중 11개에서 기대 규칙과 현재 동작의 차이를 확인했다. 실패는
컴파일·설정 실패가 아닌 각 결함의 최종 단정문에서 발생했다. 하나의 대조 함수에는
원천 교체/대상 교체 등 여러 경우가 포함된다. 기존 테스트가 통과하는 사실은 이 규칙들이
옳다는 증거가 아니며, 앞서 언급한 잘못된 기대값도 기존 검사에 포함돼 있다.

기준 커밋의 별도 깨끗한 워크트리에서 다음 명령으로 재현할 수 있다.

```sh
git apply docs/testing/effect-lifetimes/probes.patch
cargo test -p clocktower-custom-domain effect_lifetime_audit -- --nocapture
cargo test -p clocktower-domain effect_lifetime_ -- --nocapture
git apply -R docs/testing/effect-lifetimes/probes.patch
```

두 진단 명령의 실패 종료 코드는 기준 커밋의 결함을 나타낸다. 아래 패치는 그 커밋에만 적용한다.
후속 구현에서는 진단을 `issue269_effect_lifetime*` 회귀 테스트로 편입했다.


## 구현 결과 (#269)

- `EffectRule`에 유지 근거를 필수로 넣고, 기한 없음과 유지 조건 없음을 분리했다.
  발생 출처는 보존하며, 뱀조련사는 교환 결과 인스턴스, 사랑꾼은 사망 후 작동하는 원래 능력을 유지 근거로 갖는다.
- 커스텀의 중독·취함·저주·집착·주인·보호·쌍둥이 효과는 공통 유효성 평가를 이용한다.
  표식은 종료와 일시 중단을 구분한다. 동적 대상과 획득 능력 정책은 기존 캐릭터 모듈에 남겼다.
- 공식 엔진은 별도 구현으로 뱀조련사·사랑꾼의 유지 조건을 평가하고, 세레노버스의 옛 지정을
  현재 인스턴스에 재연결하지 않는다. 지정의 다음 낮·밤까지 허용하고 그 다음 낮에는 종료하는
  시간 범위도 검증한다. 새 지정이 이전 지정을 대체하며, 해가 졌다는 이유로 밤중 처형을 막지 않는다.
- 자기 중독 유지, 사랑꾼 외부 중독 후 회복, 원천 재획득, 대상만 변경, 중첩 효과, Undo,
  상호 무효화 순환을 검사한다. 과거 기록·정보는 수정하지 않는다.
- 기존 15개 진단 함수는 회귀 검사로 편입했다. 잘못된 중독 잔존을 전제로 한 공식 사랑꾼 검사도 고쳤다.

### 제공 저장본의 실제 영향

원본 92개 이벤트 중 1–28은 통과한다. **29번 몽상가 정보에서 `INVALID_DELIVERED_INFORMATION`**으로
처음 실패한다. 25번에서 뱀조련사 중독이 끝나 보르톡스가 정상 작동해야 하는데,
29번은 실제 팡 구인 2번에게 `mathematician / fangGu`라는 참인 악마 정보를 전달한 기록이다.
30번 포고꾼의 `false`와 이후의 결과를 검증하기 전에 이 불일치가 먼저 발견된다.

웹 회귀 검사는 원본을 그대로 보존한 채 재생 실패를 확인하고, 28번까지의 별도 분기에서
정상적인 거짓 몽상가 정보를 새로 확정한 다음 포고꾼 정보가 `true`로 강제되는 것을 확인한다.
임의 사망에서 정상 보르톡스를 명시적으로 선택하면 죽고, 파일 왕복 및 Undo도 일치한다.
이것은 과거 게임 자동 복구 기능이 아니다. 복구 정책과 UI는 이 변경에 포함하지 않았다.
